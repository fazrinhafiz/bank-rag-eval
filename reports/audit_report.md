## Attacks

| attack | what was done | caught by | result |
|---|---|---|---|
| UPDATE through SQL | change event 201 from reject to auto_accept with a plain UPDATE | trigger: `audit_events is append-only` | ✅ detected |
| Edit after dropping triggers | same change to event 201, triggers dropped first | `verify`: hash mismatch: event content changed or chain re-keyed (event 201) | ✅ detected |
| Delete an event | remove event 201 entirely | `verify`: sequence gap: expected 201, found 202 (event 201) | ✅ detected |
| Edit and recompute the chain | change event 201, then recompute every later hash without the key | `verify`: hash mismatch: event content changed or chain re-keyed (event 201) | ✅ detected |
| Truncate the last 10 events | delete the newest events; the shorter chain is still internally valid | not detected | ⚠️ not detected |
| Truncate the last 10 events, anchored | same, verified against the exported head (seq, hash) | `verify`: log ends at 374 but the anchor is at 384: events removed (event 375) | ✅ detected |

Truncation without an anchor is undetectable **by design of any hash chain**: what is left is a valid, shorter chain. That is why `bankrag audit head` exists: export the latest (seq, hash) on a schedule to storage the database's operators cannot rewrite (for example an object-lock bucket), and verify against it.

Recomputing the chain after an edit fails because the hashes are keyed (HMAC). With an unkeyed SHA-256 chain, that attack would succeed: the key must live in a secret store, not next to the database.
